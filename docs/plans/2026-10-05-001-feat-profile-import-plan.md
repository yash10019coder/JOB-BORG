# Phase 4: Profile Import (epic #117)

Branch: `feat/profile-import` (stacked on `feat/profile-learning` / PR #135). Rules contract: `docs/plans/2026-10-05-002-profile-import-rules.md`. Tracking issue: #136.

## Context

Phases 1-3 are built as stacked PRs (#125 → #133 → #135, all CI green, none merged). Phase 4 lets a user fill their profile from a resume, a LinkedIn PDF export, or a GitHub username, so they stop typing contact details, links, location and skills by hand, and so the system knows **which skills belong to which role or project**. The rule that governs everything: **nothing the system infers is written without the user seeing it first** (per-field and per-entry accept/reject on a review page), and **nothing imported ever overwrites what the user set, learned, or locked**.

**Decided by the user**
- **Rules first, LLM behind an allowlist.** The rule-based parser, review UI and consent ship first. The LLM path is built but stays off until providers are listed in an env setting; empty = rule-based only, fail closed.
- **Profile fields imported:** full_name, phone, current_employer, location_city, location_country, linkedin_url, github_url, portfolio_url, skills → `target_tags`, titles → `target_titles`, headline.
- **Structured resume entries (new):** **experience and projects, each with its own skills**, stored as reviewed entries. Education is **not** stored (no consumer). Years per skill are **computed in code** from the entry dates and shown to the user, but **not yet used to answer "years of X" questions**: that wiring is a follow-up after the user has seen the data quality.
- **Sources:** resume and LinkedIn PDF through one pipeline, then GitHub (public API, no OAuth) as the last unit. No scraping.

**Decided in planning (change if you disagree)**
- stdlib `re` with hard input bounds, not a new `google-re2` native dependency (FR9.3 allows "input length bounds"): text capped at 40k chars, lines over 300 chars skipped, patterns kept simple, plus an adversarial-timing test.
- A value the user **edits** on the review page is written as `source=user`; values accepted unchanged are `imported`.
- No dedicated memory-limited Celery queue now (time limits + size/page caps only).
- Entry skills are **grounded by construction**: a skill is attached to an entry only if it appears verbatim in that entry's own text block, and only if it is in the resume's own declared Skills section or the versioned skills lexicon (rules SK7/EA1). The 14-tag classification vocabulary is used **only** for `target_tags` (FK2).

## Findings that shape the design (from code exploration)
- `apply_profile_field` (apps/accounts/services/profile_fields.py) never validates values, never locks, and saves once per call; only `target_tags` among covered fields is a matching input, so batch writes into **one save**. `headline` and `target_titles` are not provenance-covered today.
- `ProfileSuggestion` is AnswerBank-question-shaped (no Profile-column support, no source), so it is **not** used for import. The new `ImportJob` payload is the proposal store.
- There is **no structured home** for experience/projects: a new `ResumeEntry` model is needed (not a JSON blob: it needs per-row provenance, dedupe, delete, and date queries for years-per-skill).
- Rule-based experience extraction is weak (the older decision notes record ~0.20 F1 for it), so entries are mostly an LLM-path win; with the LLM off, rules only catch cleanly dated layouts (LinkedIn exports are the best case: company / title / "Month YYYY - Present" lines).
- `apps.accounts` must not import `apps.auto_apply` / `apps.web`. `Profile._retire_previous_resume` already breaks this lazily, so imports must **not** go through `Profile.set_resume`; a LinkedIn PDF must never replace the user's resume.
- **The tag vocabulary is tiny and is not a skill list.** `load_ruleset()` yields only 14 job-matching tags (backend, data, design, devops, frontend, golang, high_comp, javascript, junior, kubernetes, python, remote, senior, staff). So "skills → `target_tags`" can only ever propose a handful (python, javascript, golang, kubernetes); almost every skill (Java, AWS, Docker, React, Kafka…) is not a tag. The real home for skills is the per-entry `ResumeEntry.skills`, which needs a **broader, versioned skills lexicon** plus the resume's own declared skills (rule group SK/EA in the rules doc).
- **Real-resume layout (checked on the one resume in the dev DB, letters/digits masked, no content read)**, which the rules and fixtures must reproduce: name on line 1; one pipe-separated contact line (`email | phone | linkedin | github | site`) with **scheme-less URLs** and a country-coded unspaced phone; an organization line starting with a `•` bullet, followed by a `Title - City, State  Mon YYYY – Mon YYYY` line (dates at the **end of the same line**, en dash, abbreviated months), then `◦` detail bullets; the same date-range shape inside **Education** (must not become experience); a Skills section of `Label: items` lines where several labels are **glued onto one line**, sometimes without a space after the colon; truncated/odd URLs from PDF extraction. 58 lines, 36 of them bullets, longest line 134 chars.
- No polling/JSON infra, no rate limiting, no diff CSS, no `allow_redirects=False`/size-cap HTTP precedent exist; this phase builds minimal versions of each.
- FR9.13 wants a 5 MB PDF cap but `RESUME_MAX_UPLOAD_SIZE_BYTES` is 10 MB: use a separate import setting.
- Requirements doc wording is stale: `set_profile_field` (real: `apply_profile_field`), "ProfileSuggestion for proposals", `<task_id>` in URLs (use the job UUID), and FR9.1 lists education (deferred). Fix in U10.

## Design

**Layout (all in `apps/accounts`, leaf-safe)**: `apps/accounts/importing/` with `documents.py` (safety checks, text extraction reuse, `normalize_text`), `grounding.py` (`Proposal` / `EntryProposal` with source spans; `is_grounded`), `rules.py` (profile-field rules, resume + LinkedIn layouts), `entries.py` (experience/project entry rules), `service.py` (`build_payload`, `review_rows`, `apply_review`), later `llm_extract.py` and `github.py`. `apps/accounts/services/resume_facts.py` holds entry persistence and `years_by_skill`. Tasks in `apps/accounts/tasks.py` (`run_document_import`, `run_github_import`, `sweep_import_jobs`). Web layer in `apps/web/views_import.py` + `templates/web/profile_import*.html`.

**`ImportJob`**: `public_id` (UUID, used in URLs, never the Celery id), `profile` FK, `kind` (document/github), `source_kind` (resume / linkedin_pdf / current_resume / github), `status` (pending, running, ready, applied, discarded, failed, expired), `extractor` (rule/llm), `error_code` (short code, never exception text), `source_file` (non-public, randomized name, **deleted as soon as extraction ends**), `payload` JSON, `expires_at` (24 h), timestamps. A conditional `UniqueConstraint(profile, status in [pending, running])` allows one in-flight job per profile. Payload: `{"v":1,"fields":{field:{value,snippet(≤80),extractor}},"entries":[{kind,title,organization,start,end,is_current,skills,snippet,extractor}]}`; the diff against live data is computed at render time, never stored.

**`ResumeEntry` (persisted, unlike the job payload)**: `profile` FK, `kind` (experience/project), `title`, `organization` (blank for projects), `start_date`/`end_date` (month precision, nullable; `is_current`), `skills` (JSON list of normalized names, ≤30), `source` (imported/user), `natural_key` (normalized `organization|title|start`), timestamps; `UniqueConstraint(profile, kind, natural_key)`. Apply upserts: an existing **imported** row is replaced, an existing **user** row (the user edited it on review earlier) is **kept**, nothing is deleted by a re-import. The Import tab lists stored entries with a delete button (owner-scoped POST). Editing after import is deferred.

**`years_by_skill(profile, today)`** (pure, in `resume_facts.py`): for each skill, take the date intervals of every experience entry listing it, **union overlapping intervals** (two concurrent roles do not double count), use `today` for current roles, ignore entries without dates; returns months per skill, displayed as "≈ 4.5 yrs". Not wired into the resolver in this phase.

**Entry extraction (rules, grounded by construction)**: locate the Experience/Work Experience/Employment and Projects headings; split the section into blocks at date-range lines (`Mon YYYY – Mon YYYY|Present`, `YYYY – YYYY`); title/organization come from the lines adjacent to the date line; LinkedIn layout is handled explicitly. Block text is the lines up to the next date line or heading. An entry's skills = tokens from the resume's declared Skills section ∪ the versioned skills lexicon that appear verbatim in that block (see the rules doc, rules SK/EA). Projects usually have no dates: they are a title line plus bullets, accepted by default only when a title and ≥1 skill are grounded. An entry is proposed only if its title/organization/dates are grounded; default decision is accept when it has a date range plus both title and organization, otherwise unticked.

**Profile-field rules (grounded by construction)**: every value comes from a match span in the normalized text; `is_grounded` re-checks `text[start:end]` and drops anything that fails. phone (first 15 lines, 7-15 digits), linkedin/github/portfolio URLs (https only, no userinfo, `URLValidator`), full_name (first 5 lines, 2-4 letter tokens, no digits/@/URLs), city/country (header line, only if `normalize_location` resolves), current_employer + title (from the current entry), skills (Skills section tokens in the tag vocabulary → `target_tags`), headline (LinkedIn only). Email, mailing_address and all T0/T1 fields are not imported (`IMPORTABLE_FIELDS` allowlist).

**Writing accepted values** (`profile_fields.py` additions): add `headline` and `target_titles` to `SIMPLE_FIELDS`; `import_state(profile, key)` → empty/imported/learned/user/locked, with user/learned/locked shown read-only as "Kept"; `apply_imported(profile_id, values, detail)` in one transaction with `select_for_update`: re-check state (the user may have edited in another tab), validate (`IMPORT_VALIDATORS`: https-only URLs, phone digits, alpha-3 country, list ≤50 items ≤60 chars, max lengths), stamp provenance `imported`, **save once**. Returns `(applied, kept)`. `apply_profile_field` is unchanged. Profile fields and entries are applied in **one transaction** so a failure never half-applies.

**Consent + LLM gate**: `Profile.llm_import_consent_at` / `llm_import_consent_version`; settings `PROFILE_IMPORT_LLM_ALLOWED_PROVIDERS` (env list, default empty), `PROFILE_IMPORT_LLM_PROVIDER`, `PROFILE_IMPORT_CONSENT_VERSION`. `llm_import_allowed(profile) → (bool, reason)` is true only if the provider is allowlisted and known, its API key is set, and consent exists at the current version. The task re-reads the profile and calls the gate immediately before the only call to `build_structured_model`; any failure falls back to rules. Logs carry job id, status, extractor, counts and exception class only, never text, prompts or `str(exc)`. LLM output per field and per entry is `{value(s), evidence}`; kept only if the evidence is an exact substring of the text, the value derives from it, entry skills appear in the entry's evidence, dates parse and are plausible (not future, start ≤ end), and it passes the same validators. The LLM wins for name/employer/headline and for **entries** (rules are weak there); rules win for phone and URLs.

**Abuse controls**: per-user cache counters (10 document + 10 GitHub imports/hour), the one-in-flight DB constraint, CSRF on every POST. `inspect_pdf`: `%PDF-` at offset 0, ≤ `PROFILE_IMPORT_MAX_PDF_BYTES` (5 MB), not encrypted, ≤10 pages, no `/OpenAction` `/AA` `/JavaScript` `/EmbeddedFiles` (plus a raw-byte backstop for `/JS /Launch`); DOCX uncompressed size ≤20 MB. Beat task `sweep_import_jobs` (every 15 min): expire ready jobs past TTL (clear payload, delete file), fail jobs stuck running >30 min, delete rows older than 30 days. `payload` is kept out of the admin.

**UI**: a fourth tab **Import** at `/profile/import/`: "import from my current resume" (reuses `resume_text`, no upload), an upload form (Resume or LinkedIn PDF), a GitHub username form, the consent checkbox (unchecked by default; only shown when the allowlist is non-empty), the last 5 jobs, and the **stored resume entries with derived years per skill** and a delete button each. The review page has two parts: a `<table class="diff">` for profile fields (Field | Current | Imported (editable) | Decision accept/reject radios; default accept only when the current value is empty; evidence in `<details>`) and an **Entries** list: one `.card` per entry with editable title/organization/dates/skills, accept/reject radios, "Already saved"/"Kept (you edited this)" labels. No `|safe` anywhere; about 10-15 lines of CSS in `base.html`. Apply is POST `/profile/import/<uuid>/apply/` (lock job, require ready and unexpired, rebuild a validating form so errors re-render inline, call `apply_imported` + `apply_entries` atomically, mark applied, clear payload); `/discard/` likewise. Every lookup is `get_object_or_404(ImportJob, public_id=…, profile=request.user.profile)`; entry deletes are scoped the same way.

## Risks and mitigations
- **Entry precision with rules is low** except on clean/LinkedIn layouts: everything is reviewed, defaults are conservative, and the LLM path (once enabled) improves it. Don't promise accuracy; measure on the user's own resume during manual verification.
- **A wrong year count could mislead** once it is used for answering: that is exactly why wiring is deferred until the data quality is seen.
- **Personal data at rest**: job payload snippets for ≤24 h, source file deleted after extraction; `ResumeEntry` rows are retained until the user deletes them or the account is deleted (FK cascade). Document in the PR.
- **GitHub rate limits** (60 requests/hour per server IP, shared): optional `GITHUB_API_TOKEN` (no scopes); friendly error; per-user counter.
- **LinkedIn PDF text order** varies by pypdf version: fixtures must be text from a real export with PII replaced, not hand-written guesses (manual step in U4/U4b).
- **Rematch cost**: one save per apply; `schedule_rematch` is already debounced.
- **Stacked-PR risk**: this stacks on #135 → #133 → #125 (unmerged); retarget as parents merge.
